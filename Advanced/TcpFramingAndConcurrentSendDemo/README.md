# TcpFramingAndConcurrentSendDemo

TCP Socket 编程的两个核心问题，各配一个可运行的 Demo：

1. **粘包 / 半包**：TCP 是字节流，不是消息流，必须自己划边界 → `StickyPacketDemo`
2. **并发写交织**：多个线程写同一个 Socket，大报文会在字节流里错乱 → `Sender` + `Receiver`

两者症状相似（都表现为上层解析失败），**病根却完全相反**：

| | 粘包 / 半包 | 并发写交织 |
| --- | --- | --- |
| 字节流 | **正确完整**，只是边界没标出来 | **本身就是错的** |
| 病根在 | 接收端怎么解读 | 发送端怎么产生 |
| 能否还原 | 能，分帧对了就 100% 还原 | **不能**，消息从未连续存在过 |
| 会丢数据吗 | 不会 | 会 |

把这两件事分清楚很重要：**误判成粘包，就会去加固接收端，而数据照丢不误。**

## 项目结构

| 项目 | 类型 | 职责 |
| --- | --- | --- |
| `FramingLib` | 类库 | 协议编解码、接收端分帧状态机、两种发送通道实现 |
| `StickyPacketDemo` | 控制台 | 粘包 / 半包可视化，四种分帧方案对比（单进程即可运行） |
| `Sender` | 控制台 | 监听端口，多线程并发推帧（`--mode` 切换两种写法） |
| `Receiver` | 控制台 | 连接、按帧校验、统计错帧并给出判定 |

# Demo 一：粘包 / 半包与分帧方案

```powershell
dotnet run --project .\Advanced\TcpFramingAndConcurrentSendDemo\StickyPacketDemo
```

先把现象显示出来——同一次传输里每次 `Receive` 的真实情况：

```text
第几次读   读到字节   解析出消息   半包残留   现象
1          4096       21           3090       粘包
2          4096       0            7186       半包
3          4096       0            11282      半包
4          4096       0            15378      半包
5          4096       0            19474      半包
6          1499       21           0          粘包
```

**读取边界和消息边界毫无关系**：第 1 次读就拿到 21 条完整消息（粘包），
中间连续 4 次读一条都凑不齐（半包，大消息还在累积）。

然后用同一批消息对比四种处理方式：

```text
方案              解析条数    内容正确    发送字节     放大
朴素(无分帧)       6/42       0/42       21,433      1.00x
固定长度(20000B)   42/42      42/42      840,000     39.19x
分隔符             43/42      20/42      21,475      1.00x
长度前缀           42/42      42/42      21,979      1.03x
```

四个结论：

- **朴素方案**解析出的条数等于 `Receive` 次数（6 次），和消息数毫无关系
- **固定长度**结果正确，但要按最大消息补齐，这里放大了近 40 倍
- **分隔符**被一条内容里含换行的"陷阱消息"切成两条（43 条），
  此后所有消息全部错位——一次误切就让整条流失去同步，这是它不二进制安全的代价
- **长度前缀**完全正确且几乎没有开销，是绝大多数自定义协议的选择

关键点：**粘包不丢数据**。字节一个不少地到达，只要边界划对就能 100% 还原。

### 三种分帧方案怎么选

| 方案 | 优点 | 代价 | 典型场景 |
| --- | --- | --- | --- |
| 固定长度 | 实现最简单 | 按最大消息补齐，浪费严重；超长放不下 | 定长指令、嵌入式 |
| 分隔符 | 省空间，可读性好 | 内容含分隔符要转义，非二进制安全 | HTTP 头、Redis RESP |
| 长度前缀 | 二进制安全，无需扫描 | 需要几字节帧头 | 绝大多数自定义协议 |

`StickyPacketDemo` 里的长度前缀方案直接复用了 `FramingLib` 的帧格式，
也就是下面并发写 Demo 用的同一份实现。

# Demo 二：多线程并发写同一个 Socket

## 运行

开两个终端，先起发送端（它会等待连接），再起接收端：

```powershell
# 终端 1：裸并发写（有缺陷的写法）
dotnet run --project .\Advanced\TcpFramingAndConcurrentSendDemo\Sender -- --mode unsafe

# 终端 2
dotnet run --project .\Advanced\TcpFramingAndConcurrentSendDemo\Receiver
```

发送端按固定周期一轮一轮地推（和真实推送服务一个形态），默认一直推到 Ctrl+C：

```text
[第   1 轮] 本轮 16 帧，累计 16 帧
[第   2 轮] 本轮 16 帧，累计 32 帧
```

接收端持续接收，错帧一出现就立刻报出来，便于对上发送端是哪一轮：

```text
  !! 检测到错帧，累计 1 个（已丢弃 66,625 字节）
  !! 检测到错帧，累计 2 个（已丢弃 133,788 字节）
  [累计] 完整 20 帧，错帧 2，收到 543,136 字节
```

Ctrl+C 结束后输出汇总：

```text
完整接收帧数      49
    其中 256 B 帧   34
    其中 64 KB 帧   15
错帧(结束符不符)  5
重同步丢弃字节    334,739
--------------------------------------------------------------
检测到报文交织：发送端存在多线程并发写同一个 socket 的问题。
```

把发送端换成 `--mode queued` 再跑一次，同样 5 轮：

```text
[第   5 轮] 本轮 16 帧，累计 80 帧，队列积压 713 KB

完整接收帧数      80
    其中 256 B 帧   60
    其中 64 KB 帧   20
错帧(结束符不符)  0
重同步丢弃字节    0
--------------------------------------------------------------
所有帧均完整且内容正确，未发现交织。
```

队列模式下能顺带看到**积压随轮次增长**——接收端消费不过来时，数据堆在应用层队列里，
这正是背压机制要守住的地方（超过上限即断开慢消费者）。

接收端用退出码区分结果：`0` 正常，`2` 检测到交织，便于接到脚本里做回归。

### 调试用法

发送端是「轮询 + 批量推送」结构，适合挂断点慢慢看：

- 断点打在 `Sender/Program.cs` 的 `SendOneRound(round)` 调用处，**每轮停一次**
- 步入 `SendOneRound`，能看到多个线程如何并发写同一个 socket
- 线程名带轮次（`Bulk0-R3`、`Small1-R3`），调试器的线程窗口里一眼能分辨

两个专门为调试做的处理：

- **接收端不会因超时退出**。`Receive` 超时只是继续等待，所以你在发送端停留多久都没关系
  （实测发送端每轮停 12 秒、接收端超时 5 秒，接收端完整撑过全程）。
  只有读到流结束或 Ctrl+C 才会收尾。
- **发送端长时间停留**可能触发 `SendTimeout`（默认 30 秒）导致连接判废，
  需要长时间单步时用 `--send-timeout-ms` 调大。

常用参数：

```text
Sender    --mode unsafe|queued   --interval-ms 1000   --rounds 0(一直推)
          --bulk-frames 4        --small-frames 4     --bulk-size 65536
          --chunk-size 8192      --send-timeout-ms 30000
Receiver  --read-delay-ms 1      --read-chunk 4096    --report-interval-ms 3000
两端通用  --port 19869
```

## 为什么并发写会出问题

```
线程A: [帧A块1][帧A块2]        [帧A块3]...
线程B:                 [帧B完整]
实际流: [帧A块1][帧A块2][帧B完整][帧A块3]...
                        ↑ 帧A 被劈成两半，中间插入了帧B
```

关键在于**一次 Send 未必是一次写入**：

当帧大于发送缓冲区剩余空间时，阻塞模式下的 `send()` 会进入等待。
而等待期间内核会**释放 socket 锁**（Linux 的 `sk_stream_wait_memory`），
于是另一个线程的 `send()` 可以拿到锁、把自己的字节追加进去。

小包为什么没事：一次就能塞进缓冲区，单次写入是原子的。
所以触发条件是"报文大到必须分多次写出"——报文随业务增长变大的那天，就是爆发之日。

接收端按长度字段切包，切出来的内容中间混着别的帧，
表现为上层反序列化（JSON / Protobuf）报出各种看不懂的解析错误。
排查时往往只能看到一坨几十 KB 的畸形报文，很难第一时间联想到发送端的并发问题。

Demo 刻意还原真实事故的流量配比：**一条线程推 64 KB 大帧，三条线程推 256 B 小帧**。
小帧一次就能写完，本身是原子的；但它插进大帧的分块之间，**被毁掉的是那个大帧**。
于是出现一个反直觉的现象：**出问题的总是最大的那类报文，而"肇事者"是最不起眼的心跳包**。
被插入的小帧随后也会在重新同步时被一起丢弃，所以小帧的接收数同样会掉。

### 平台差异（本 Demo 的一个实测发现）

同样一份有缺陷的代码：

- **Linux**：`send()` 等待缓冲区时释放 socket 锁，并发写会交织 → 复现
- **Windows**：Winsock 对同一 socket 的并发 `send` 有自己的串行化 → 不复现

实测在 Windows 上用真实并发 `send` 压测，发送端确实被阻塞（队列峰值积压 6.4 MB），
却**一帧都没有交织**。这解释了为什么这类缺陷常常"本地测不出、上了 Linux 才爆发"。

因此 Demo 用 `SocketWriter.WriteChunked` **显式分块**写出，
忠实还原内核在缓冲区满时的行为，让现象在任意平台都能确定性复现。

## 修复：每连接一条发送队列

```
业务线程 ──┐
业务线程 ──┼──> 发送队列 ──> 专属发送线程 ──> Socket
业务线程 ──┘    (有界，带背压)   (唯一写入者)
```

解决三件事：

| 问题 | 解法 |
| --- | --- |
| 交织 | 实际写 socket 的只有一个线程，物理上杜绝 |
| 慢消费者拖垮全局 | 业务线程只入队，不被阻塞 |
| 无限积压 OOM | 积压超上限即断开，让对端重连 |

**不要用加锁代替队列**：加锁同样能串行化，但业务线程会排在大帧后面，
一个慢消费者就能拖住所有推送线程。

## 接收端要做的四件事

| 情况 | 处理 |
| --- | --- |
| 粘包（一次读到多帧） | 循环切，直到切不动 |
| 半包（帧没收全） | 保留在缓冲区等后续数据 |
| 脏数据（对不上 Magic） | 扫到下一个结束符重新对齐 |
| 错帧（长度指向处不是结束符） | 判定交织错位，丢弃并重新同步 |

最后一条最容易被忽略。帧格式里**同时有长度字段和结束符**，是因为两者职责不同：

- 长度字段负责**切得快**
- 结束符负责**切得对**——用来校验这一帧是否真的完整

只校验长度不校验结束符，错位的脏数据会被当成正常内容交给上层，
等上层解析失败时，现场信息已经丢了。

另外必须校验长度字段的合法性：长度一旦被污染会变成一个巨大的数，
没有上限保护，接收端会一直等"永远凑不齐的一帧"，直到缓冲区被撑爆。

## 帧格式

```text
+--------+---------------+--------+-----------+--------+
| Magic  | PayloadLength | Type   | Payload   | Tail   |
| 4 字节 | 4 字节        | 4 字节 | N 字节    | 1 字节 |
| "DEMO" | N             | int    | ...       | '$'    |
+--------+---------------+--------+-----------+--------+
```

Demo 把负载大小写进 `Type` 字段，接收端据此区分大帧和小帧，无需额外配置。

## 其他容易踩的坑

- **必须设 `SendTimeout`**：对端假死（TCP 窗口归零）时 `Send` 会无限阻塞，
  发送线程被永久挂住，且外部看不出异常。
- **`SendBufferSize` 未必生效**：Linux 上 `setsockopt(SO_SNDBUF)` 会被
  `net.core.wmem_max` 截断（默认约 208 KB），代码里设 4 MB 实际并不会生效。
- **异步发送队列必须有优雅关闭**：直接关连接会把队列里的尾部数据丢掉，
  见 `IFrameSession.Flush`。
- **写失败后不要继续发**：此时可能只发出了半帧，继续写会让对端一直错帧，
  应判定连接报废并断开。
- **`Send` 的返回值是实际写出字节数**：不处理部分写入（例如
  `socket.Send(frame) > 0` 就当成功）会静默丢数据。
- **关闭要用 `Shutdown(SocketShutdown.Send)`**：发 FIN 让对端读到干净的流结束，
  比靠超时判断可靠得多。

## 可替换点

- `FrameCodec` 的定长头可换成 Protobuf varint、HTTP/2 帧头等其他分帧方案
- `QueuedSession` 的背压策略可改为丢弃最旧帧、降采样，而非直接断连
- 调整 `--chunk-size` / `--bulk-size` / `--read-delay-ms` 可观察各条件对复现概率的影响
